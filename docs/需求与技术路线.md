# 通用产品需求与技术路线

## 产品目标

建设一个成熟的开源审阅桥接工具，使任意合规的 LaTeX 论文项目都可以经过可复现、可审计的流程交给 Word 用户审阅，并把返回的修订安全地映射回 LaTeX。

本项目追求内容、结构和审阅证据的可靠对应，不追求 PDF 到 Word 的像素级复刻。单篇私人论文只是压力测试，不得成为公共接口或实现中的特例。

## 用户场景

1. 作者检查环境并冻结 LaTeX 审阅基线。
2. 作者选择转换后端，生成可编辑、可核验、带稳定审阅锚点的 Word。
3. 导师或合作者只使用 Word 修订和批注。
4. 作者导入返回文件，得到包含作者、时间、插入、删除、移动和批注的结构化账本。
5. 作者逐条接受、拒绝或标记人工处理。
6. 工具只把已批准且可安全定位的变更应用到 LaTeX 工作副本。
7. 工具重新编译并生成引用检查、结构检查和 `latexdiff` 证据。

最终回填交付固定分为三层：

- `revised-clean/`：只包含已批准内容的正式 LaTeX 工作副本；
- `diff/revisions.tex` 与 `diff/revisions.pdf`：基于审阅基线生成的可视化增删标记；
- `change-ledger.json/html`：保留作者、时间、批注、原文、新文、定位证据和审批状态。

可选生成使用 `changes` 宏包区分不同审阅者的标记版，但它只作为派生审阅产物，不进入权威源码。

## 交付边界

### 核心项目

核心采用 Python 库和稳定 CLI。业务逻辑、安全约束和 Schema 全部位于核心项目中，任何用户、CI 或 Agent 都能在不使用 Codex 的情况下运行。

当前公共命令：

```text
latex-word-review new-run
latex-word-review doctor
latex-word-review snapshot
latex-word-review export
latex-word-review inspect
latex-word-review reader-capabilities
latex-word-review archive
latex-word-review ingest
latex-word-review approve init|set|finalize|serve
latex-word-review plan
latex-word-review apply
latex-word-review verify
latex-word-review ledger
latex-word-review run-manifest
latex-word-review bundle|verify-bundle
latex-word-review validate
```

业务命令的 stdout/stderr canonical JSON、稳定退出码和版本化 JSON Schema 是机器接口；
`--help`、`--version` 与 argparse 语法错误的面向人文本不作为机器兼容承诺。

## 逐条审批的操作方式

审批与应用必须是两个独立动作，避免用户点击“接受”时立即改动 LaTeX。

### 本地浏览器界面（主要入口）

执行 `latex-word-review approve serve CHANGESET APPROVAL OUTPUT_DIR --open-browser` 后，只在
`127.0.0.1` 启动本地页面，不上传论文。页面按变更卡片展示：

- Word 中的前后文和红绿差异；
- 作者、时间、批注和原始证据；
- 对应 LaTeX 文件、行号或标签；
- 定位置信度和安全等级；
- `接受`、`拒绝`、`接受并修改文本`、`转人工处理` 四种操作。

页面支持逐项导航；CLI/库只有在调用方明确给出 exact plain-text policy 时才允许低风险
批量决定。公式、引用、编号、复杂表格、冲突和低置信度项必须单独处理。

### CLI 与 Codex

CLI 提供同一状态机的非图形入口，适合自动化和无界面环境。Codex Skill 允许用户用自然语言表达“接受 CHG-001 和 CHG-004，拒绝 CHG-002，其余保留待处理”，但最终仍写入同一种审批文件，不绕过核心规则。

### 两道闸门

第一道闸门只记录决定，生成 `approval.json`，至少包含 `change_id`、决定、决定者、决定时间、原因、最终文本和原始 `ChangeSet` 哈希。此时 LaTeX 完全不变。

随后 `latex-word-review plan` 根据审批结果生成 `patch-plan.json` 和 `changes.patch` 供预览。
第二道闸门由 `latex-word-review apply` 执行：它重新核对基线、账本和审批文件哈希，只向
新的工作副本应用补丁。任何文件漂移、冲突或未批准项都会阻止应用。

### Codex Skill

仓库提供薄 `latex-word-review` Skill。Skill 只负责识别阶段、调用 CLI、解释报告和在审批
点暂停，不直接解析 OOXML、修改 `.tex` 或拼接转换命令。

## 复用优先架构

```text
CLI / Python API / Codex Skill / CI
                 ↓
        审阅状态机与运行记录
                 ↓
 ReviewIR / SourceMap / ChangeSet / PatchPlan
                 ↓
 转换后端 | DOCX 解析器 | LaTeX Profile | 验证器
```

第一轮上游结论：

- `tex2word` 作为优先主转换后端候选；
- Pandoc + pandoc-crossref/`latex2word` 作为独立基线；
- Pandoc `--track-changes=all`、`docx-revisions` 和 `docx-mcp` 作为修订提取候选；
- `docXMLater` 作为 OOXML 保真设计和测试思路参考；
- 不采用任意 DOCX 整篇反向生成 LaTeX 的路线。

项目不复制第三方核心转换逻辑。对上游缺失的通用能力优先贡献；本项目只实现审阅工作流特有的稳定接口、安全策略和适配层。

## 稳定领域模型

至少定义并版本化：

- `RunManifest`：运行 ID、工具链、配置、产物和校验和；
- `SourceManifest`：LaTeX 项目文件图、来源和冻结哈希；
- `ReviewIR`：与后端无关的审阅语义；
- `SourceMap`：`unit_id` 到源文件、源码范围和上下文指纹的映射；
- `ExportReport`：转换指标、失败和降级项；
- `ChangeSet`：Word 修订与批注的原始证据及定位结果；
- `PatchPlan`：逐条接受状态、安全等级和候选局部补丁；
- `VerificationReport`：编译、引用、资源、结构和差异核验结果。

每个 `ChangeSet` 项至少包含：

```text
change_id, kind, author, timestamp, unit_id, source_location,
before, after, comment, confidence, resolution_method,
safety_class, status, evidence
```

## 审阅单元和定位

导出时把标题、段落、列表项、图题、表题、表格单元、公式容器和引用等转换成稳定审阅单元。每个单元同时获得：

- 可写入 DOCX 的书签或自定义属性；
- 独立 `source-map.json` 记录；
- 原始 LaTeX 切片和规范化文本；
- 源文件位置、邻接单元和内容指纹；
- 自动回填安全等级。

锚点缺失时允许使用邻接关系和文本指纹回退匹配，但必须输出置信度。低置信度、冲突或高风险变更只能进入人工队列。

## 不可变运行目录

```text
runs/<run-id>/
  snapshot/
  objects/source-manifest.json
  export/review.docx
  export/objects/source-map.json
  returned/returned-original.docx
  objects/changeset.json
  approvals/approval-r1.json
  plan/patch-plan.json
  plan/changes.patch
  revised/
  verification/verification-report.json
  verification/latexdiff.pdf
  ledger/ledger.json
  objects/run-manifest.json
  audit.zip
```

返回 Word 原件只读归档；任何规范化、接受或拒绝操作只作用于派生副本。

## 非目标

- 支持所有 TeX 宏包和任意自定义宏；
- PDF 到 Word 的像素级复刻；
- 把任意来源 DOCX 自动恢复成原始 LaTeX；
- 整篇重写或覆盖 LaTeX；
- 自动应用公式、引用、编号和复杂表格修改；
- 在宿主机无隔离地执行不可信 LaTeX；
- 为单个期刊或私人论文硬编码规则。

## 测试策略

公开仓库使用自制或许可明确的最小特性语料，覆盖：Unicode、多文件、宏、公式、标签、引用、子图、复杂表格、脚注、算法、插入、删除、移动、批注、锚点损坏和冲突。

私人论文仅在 `samples/` 中做本地压力测试，不进入 Git。测试比较规范化 OOXML、结构指标、Schema 和语义结果，不依赖 DOCX ZIP 的非确定性字节差异。

## 实施阶段

1. 完成上游能力、许可证和契约评估，冻结 adopt/wrap/contribute/self-build 决策。
2. 冻结 CLI、Schema、运行目录、错误码和后端能力接口。
3. 实现 `doctor`、不可变快照、文件图和审阅单元 ID。
4. 接入 `tex2word` 主后端与 Pandoc 基线，生成统一报告。
5. 完成完整修订/批注提取和 `ChangeSet`。
6. 完成普通正文的逐条补丁计划、dry-run 和受控回填。
7. 完成编译、引用、结构和 `latexdiff` 核验。
8. 建立跨平台 CI、公开语料、贡献规范和 beta 发布。
9. CLI 稳定后初始化并前向测试 Codex Skill。
